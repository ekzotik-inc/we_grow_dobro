# Каркас Telegram-бота

Что доказано на боевом проекте и переносится в следующий без изменений.
Подробности: `references/architecture.md`, `references/deploy.md`, `references/pitfalls.md`.

Стиль сообщений и кнопок — в отдельном навыке `tg-bot-style`.

## Стек

- **Python 3.11+, aiogram 3** (long polling), **SQLAlchemy 2 async**, **APScheduler**,
  **FastAPI + uvicorn** — служебный порт, чтобы хостинг видел живой сервис.
- **База:** SQLite локально, PostgreSQL на хостинге — переключается одной переменной
  `DATABASE_URL`, код одинаковый. Оба варианта прогоняются автотестом.
- Один процесс: `python -m app.main` поднимает бота, планировщик и веб-сервер.

## Структура

```
app/
  config.py       все настройки из переменных окружения, ничего в коде
  models.py       модели SQLAlchemy
  db.py           движок, сессии, автомиграция, первичное наполнение
  services.py     бизнес-логика: чистые функции над сессией, без Telegram
  texts.py        все тексты, HTML
  keyboards.py    все клавиатуры
  emoji.py        премиальные эмодзи и замены
  export.py       выгрузка в Excel
  scheduler.py    фоновые задачи
  bot/
    handlers/     роутеры по темам
    middlewares.py
    channels.py   карточки в каналах модерации
    common.py     session(), edit(), якорное сообщение
data/             контент проекта (задания, наборы эмодзи, картинки)
scripts/          smoke_test, preview, preflight, аудиты, генераторы картинок
```

Правило: **логика в `services.py`, Telegram — в `handlers/`.** Тогда бизнес-правила
тестируются без бота, а обработчик остаётся в десяток строк.

## Настройки

Всё, что может измениться, — переменная окружения со здравым значением по умолчанию.
Никаких id, дат, ссылок и лимитов внутри кода.

Обязательный минимум: `BOT_TOKEN`, `DATABASE_URL`, `ADMIN_IDS`, `TZ`.
Дальше по проекту: каналы, контакты поддержки, периоды, часы рассылок, размер команды.

Боевые id владельца и поддержки полезно продублировать значением по умолчанию: если
переменная потеряется при переезде, панель не откроется всем подряд.

## Уровни доступа

Три уровня, и они не совпадают:

| Уровень | Кто | Что может |
|---|---|---|
| Пользователь | все | всё, кроме панели |
| Модератор | `PC_IDS` | `/admin`: заявки, проверка, справочники |
| Владелец | `ADMIN_IDS` | плюс скрытая команда правки уже начисленного |

Права даёт **только список в настройках**, никогда — флаг в базе: флаг переживает
переезды и достаётся не тем людям. При старте флаги в базе приводятся к спискам.

Команды прячутся через области видимости: `BotCommandScopeAllPrivateChats` для всех,
`BotCommandScopeChat` — персонально сотрудникам. Скрытая команда не публикуется вообще.

Фильтр доступа объявляется **наследником `BaseFilter`**. Класс с методом `__call__`
не годится: aiogram не дождётся корутины и посчитает проверку пройденной.
Проверять права нужно прогоном обновления через диспетчер, а не вызовом фильтра.

## Модерация через каналы

Заявки и результаты публикуются карточками в двух каналах, решение принимается кнопкой
прямо там. После решения бот **редактирует ту же карточку**: кнопки исчезают, остаётся
кто, когда и с какой причиной решил — канал становится журналом.

- канал не привязан → карточки уходят модераторам в личку, бот работает и так;
- id каналов задаются и переменной окружения, и из панели (переменная переживает смену базы);
- у кнопок в каналах обязателен фильтр доступа: канал видят многие.

## База и миграции

Инструмента миграций нет — есть **аддитивная автомиграция** на старте: код сравнивает
модели с таблицами и добавляет недостающие колонки. Этого хватает, если новые поля
всегда nullable или со значением по умолчанию.

Требования к автомиграции: понимать `default=list` / `default=dict` (JSON-колонки иначе
молча не создаются) и `NOT NULL` со значением по умолчанию. Переименование и удаление
колонок — только руками и осознанно.

## Рассылки

- каждая рассылка отмечается в таблице `broadcasts` с ключом вида `weekly:2026-09-14` —
  повтор за тот же день невозможен, даже если сервис перезапустился;
- отправка с паузой ~50 мс (лимит Telegram ~30 сообщений в секунду);
- сбой доставки одному человеку не останавливает рассылку;
- у каждой автоматической рассылки есть ручная кнопка в панели.

## Обязательные проверки

Скрипты, которые окупаются с первого дня:

```bash
python -m scripts.smoke_test       # бизнес-логика, права, миграции — на SQLite и PostgreSQL
python -m scripts.audit_callbacks  # каждая кнопка нажимается от лица трёх ролей
python -m scripts.audit_texts      # HTML и лимиты длины на каждом экране
python -m scripts.preview          # все экраны текстом, прочитать глазами
python -m scripts.audit_pushes     # уведомление пользователю на каждое решение модератора
python -m scripts.preflight        # готовность к запуску: настройки, каналы, контент
```

`audit_callbacks` находит то, что не находит ничто другое: кнопку без обработчика и
падение на пустых данных. `preflight` печатает список того, что человек должен сделать
руками перед запуском.

## Порядок работы над новым ботом

1. Модели и `services.py` — бизнес-правила без Telegram, сразу с автотестом.
2. Тексты и клавиатуры по навыку `tg-bot-style`.
3. Обработчики: тонкие, только связка «событие → сервис → экран».
4. Каналы модерации и уровни доступа.
5. Планировщик и рассылки.
6. Аудиты и `preflight`, затем деплой.
7. Материалы для людей: описание бота, картинки профиля, презентация, памятка.
